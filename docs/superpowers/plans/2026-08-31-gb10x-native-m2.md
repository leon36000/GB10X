# GB10X Native M2 Implementation Plan

> **Execution status:** host correctness and CUDA `sm_121a` compile/link are verified. Real DGX Spark / GB10 device execution remains pending and is intentionally a separate proof class.

**Goal:** Establish the first real GB10-native execution layer: strict CUDA `sm_121a` toolchain/build gates, a versioned native ABI and probe, an executable CUDA smoke path, exact safetensors-backed PLE row access, and the first correctness-gated CUDA model kernel without making any unverified performance claim.

**Architecture:** Host-independent Rust logic is testable on ordinary CI. Native CUDA exists only behind the `native-cuda` feature in `gb10x-cuda`; there is no CPU fallback pretending to be CUDA. A stable C ABI hides CUDA/C++ ABI details from Rust. Every native object is compiled specifically for `compute_121a -> sm_121a`. Host correctness, CUDA compile/link, and real-GB10 execution are separate proof classes.

**Tech Stack:** Rust 1.98+/edition 2024, CUDA C++/CUDA Runtime API, `nvcc`, CUDA 12.9+ for `sm_121a`, BF16, safetensors parsing, mmap, SHA-256, GitHub Actions host gates, pinned CUDA compile container, DGX Spark native evidence script.

**Spec:** `docs/superpowers/specs/2026-08-31-gb10x-cache-first-v3-design.md`

## Global Constraints

- Production target: NVIDIA GB10 / DGX Spark only, Linux `aarch64`, CUDA `sm_121a`.
- Model target: `Qwen/Qwen3.8-Flash-Next` only; immutable architecture/source mismatches fail closed.
- Minimum native compiler for M2: **CUDA 12.9**. CUDA 12.8 is rejected because it does not provide the required `sm_121a` compiler target.
- Native CUDA is opt-in through `native-cuda`; ordinary host CI must remain CUDA-independent.
- No CPU/mock/stub backend may satisfy a CUDA capability or device-execution gate.
- No compatibility target for other GPUs is added in M2.
- No tokens/second, latency, bandwidth, cache-hit-rate, or speedup claim is permitted in M2.
- Every production behavior change follows RED -> verify RED -> minimal GREEN -> full applicable gates.
- Checkpoint/source identity is pinned before model files are bound.

## Task 1 — Strict CUDA build/toolchain contract

**Status:** **COMPLETE / HOST VERIFIED**

Implemented in `crates/gb10x-cuda`:

- `CudaArchTarget::Gb10Sm121a`;

- tests proving CUDA 12.8 is rejected and CUDA 12.9 is accepted.

No CUDA headers or libraries are required for this pure-Rust contract.

## Task 2 — Native CUDA C ABI and device probe

**Status:** **IMPLEMENTED / HOST + CUDA COMPILE-LINK VERIFIED / DEVICE EXECUTION PENDING**

Implemented:

- feature `native-cuda`;
- stable version-1 C ABI `gb10x_cuda_device_info_v1`;
- Rust `CudaDeviceInfoRawV1`, `CudaDeviceInfo`, and fail-closed conversion validation;
- `gb10x_cuda_probe_device` using CUDA Runtime properties/attributes;
- Rust `probe_device(ordinal)` wrapper;
- `build.rs` no-op without the feature and strict native build with the feature;
- architecture-specific compilation with `--generate-code=arch=compute_121a,code=sm_121a`;
- static ABI size/offset assertions on the CUDA/C++ side.

The Rust validation requires:

- ABI version 1;
- non-negative ordinal;
- compute capability exactly 12.1;
- nonzero total memory, L2, SM count, and warp size;
- persisting-L2 maximum not exceeding discovered L2;
- NUL-terminated, valid UTF-8, non-empty device name.

No published GB10 cache or memory capacity is hard-coded as a runtime fact.

**Pending device proof:** execute `probe_device(0)` on the actual Spark and observe CC 12.1 and discovered properties.

## Task 3 — Native CUDA facts in `gb10x-probe --json`

**Status:** **IMPLEMENTED / HOST + CUDA COMPILE-LINK VERIFIED / DEVICE EXECUTION PENDING**

Without `native-cuda`, JSON explicitly reports:

```json
{
  "cuda_native": {
    "state": "unavailable",
    "reason": "binary built without native-cuda feature"
  }
}
```

It never fabricates a GPU snapshot.

With `native-cuda`, the production CLI:

1. probes the Linux host;
2. calls the real `probe_device(0)` native CUDA path;
3. converts only those native facts to `GpuSnapshot`;
4. runs `validate_gb10`;
5. renders `cuda_native.state = "verified"` only after those operations succeed.

A synthetic CUDA-build test verifies the mapping/JSON contract without pretending to be hardware evidence.

## Task 4 — Executable `sm_121a` CUDA smoke kernel

**Status:** **IMPLEMENTED / CUDA COMPILE-LINK VERIFIED / DEVICE CORRECTNESS PENDING**

C ABI:

```c
int gb10x_cuda_smoke_v1(uint64_t elements, uint64_t* checksum);
```

Rust:

```text
run_smoke(elements: u64) -> Result<u64, CudaNativeError>
```

The native path:

- allocates a device buffer;
- writes deterministic 64-bit values in a CUDA kernel;
- rereads the buffer in a separate reduction kernel;
- reduces with wrapping 64-bit addition;
- synchronizes and returns only the 64-bit checksum to the host;
- propagates allocation/launch/synchronization/copy/free failures.

The test independently computes the expected checksum for `1 << 20` elements.

**Pending device proof:** run `native_smoke` on GB10 and compare the GPU checksum against the independent CPU oracle.

## Task 5 — Exact safetensors-backed PLE source

**Status:** **COMPLETE / HOST VERIFIED**

Implemented:

- read-only mmap safetensors source;
- checked header/data offsets and integer arithmetic;
- BF16 enforcement;
- two-dimensional `[rows, 160]` geometry enforcement;
- overlap/truncation/out-of-range rejection;
- exact row reads across physical PLE shard boundaries;
- SHA-256 provenance binding manifest/revision plus exact referenced PLE tensor bytes;
- safe relative file paths only.

Pinned Qwen PLE contract:

- model id: `Qwen/Qwen3.8-Flash-Next`;
- revision: `34567a4712bc9766c4449e2e98e4468bfa24d915`;
- 128 physical PLE parts;
- 2,500,012 logical rows per part;
- 320,001,536 total logical rows;
- 160 BF16 elements per row;
- tensor prefix `model.language_model.layers.1.ple.ple_embedding.ngram_embedding.shard_` with canonical indices `0..127`.

The manifest is derived from the checkpoint's own `model.safetensors.index.json`; GB10X does not rely on a hard-coded table of safetensors filenames.

Actual appliance checkpoint-byte binding remains a deployment/device-side action and must match the pinned revision.

## Task 6 — First correctness-gated model kernel: BF16 RMSNorm

**Status:** **IMPLEMENTED / CUDA COMPILE-LINK VERIFIED / DEVICE NUMERICAL CORRECTNESS PENDING**

Contract:

- Qwen width = 2560;
- epsilon = `1e-6`;
- BF16 input/weight/output;
- FP32 accumulation;
- production API is pointer/device-buffer oriented;
- a host-vector helper exists only to drive the real CUDA correctness test.

Kernel design:

- one block of 256 threads for one row;
- strided FP32 sum-of-squares accumulation;
- shared-memory tree reduction;
- reciprocal RMS computed in FP32;
- BF16 output with round-to-nearest-even conversion.

Correctness test vectors:

- zero;
- constant;
- alternating-sign;
- deterministic pseudo-random.

The CPU oracle performs FP32 accumulation and BF16 rounding. The approved comparison gate is **<= 1 BF16 ULP** per output element.

**Pending device proof:** execute the RMSNorm test on GB10. Compile/link success does not establish numerical correctness.

## Task 7 — M2 evidence workflow and native handoff

**Status:** **IMPLEMENTED / HOST VERIFIED / DEVICE EXECUTION PENDING**

Files:

- `scripts/verify-gb10-m2.sh`;
- `docs/evidence/m2-native-verification.md`;

Host CI proves the verifier:

- has valid Bash syntax;
- rejects non-Linux/non-`aarch64` hosts before native work;
- leaves the ordinary Rust workspace gates green.

On the real DGX Spark, run from an exact clean source commit:

```bash
bash scripts/verify-gb10-m2.sh
```

The verifier fail-closes unless all of the following pass:

- Linux `aarch64`;
- required tools present;
- clean tracked source state and exact Git SHA binding;
- CUDA compiler >= 12.9;
- `nvidia-smi` availability;
- native `gb10x-probe --json` state `verified`;
- device identity containing GB10;
- compute capability exactly 12.1;
- nonzero discovered memory/L2/SM/warp facts and coherent persisting-L2 value;
- `validate_gb10` success;
- native device-probe test;
- deterministic smoke checksum test;
- BF16 RMSNorm correctness test;
- `cuobjdump --list-elf` inspection of `probe.o`, `smoke.o`, and `rmsnorm.o`.

Only after all gates pass does the script write `summary.json` with:

```text
proof_class = gb10-device-execution
result = pass
performance_claim = null
```

Raw logs and a human-readable summary are retained in the evidence directory.

## M3 Boundary

M2 intentionally does not implement full Qwen inference, production attention/MoE scheduling, MTP/speculative decoding, CUDA Graph supergraphs, cache-policy tuning, ARM/SVE kernels, serving, or end-to-end tokens/second optimization. Those belong to later milestones after the real Spark correctness gate is captured.

## Plan Self-Review

- M2 stays bounded to the native execution foundation.
- No CUDA runtime claim is produced by x86 host CI or compile-only CUDA CI.
- No generic GPU/model abstraction is introduced.
- The safetensors task closes the M1 gap between prepared flat PLE rows and the real model format.
- RMSNorm is intentionally the first model-math kernel because its oracle is compact and isolates CUDA ABI/memory/reduction correctness before attention/MoE complexity.
- All native paths are real CUDA or absent; no fake backend exists.
